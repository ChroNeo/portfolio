## Problem Statement

### ปัญหาและผลกระทบ

การจัดนิทรรศการและกิจกรรมในปัจจุบันยังพึ่งพากระบวนการแบบกระจัดกระจาย ผู้เข้าร่วมลงชื่อบนกระดาษหน้างาน ทำแบบประเมินผ่านลิงก์อีกช่องทาง แล้วรอรับเกียรติบัตรทางอีเมลอีกหลายวันให้หลัง ขณะที่ผู้จัดงานต้องนำข้อมูลจากทุกช่องทางมารวมด้วยมือ เพื่อตรวจสอบว่าใครเข้าร่วมครบตามเกณฑ์บ้าง

| ฝั่งผู้จัดงาน                                            | ฝั่งผู้เข้าร่วม                                    |
| -------------------------------------------------------- | -------------------------------------------------- |
| ต้องรวมข้อมูลจากหลายระบบด้วยมือ เสี่ยงตกหล่นและซ้ำซ้อน   | ไม่รู้ว่าตัวเองเข้าร่วมครบตามเกณฑ์แล้วหรือยัง      |
| ไม่เห็นยอดผู้เข้าร่วมระหว่างงาน ปรับแผนหน้างานไม่ได้     | ต้องเดินไปถามทีมงาน หรือรอให้ประกาศผล              |
| ออกเกียรติบัตรทีละใบ ใช้เวลานานและพิมพ์ชื่อผิดบ่อย       | ได้รับเกียรติบัตรช้า บางครั้งชื่อสะกดผิดต้องขอแก้  |
| ใช้กระดาษจำนวนมากทั้งใบเซ็นชื่อและเกียรติบัตร            | ทำเอกสารหายแล้วขอใหม่ไม่ได้                        |

### ทางเลือกที่มีอยู่ไม่ตอบโจทย์

ระบบจัดการงานอีเวนต์ที่มีในตลาดมักอยู่ในรูปแบบแอปพลิเคชันที่ต้องติดตั้งและสมัครสมาชิกใหม่ ซึ่งเป็นอุปสรรคสำคัญกับงานที่มีผู้เข้าร่วมหลากหลายกลุ่มและใช้งานเพียงครั้งเดียว ผู้เข้าร่วมจำนวนมากไม่ยอมโหลดแอปเพื่อร่วมงานเพียงวันเดียว ทำให้ระบบถูกใช้งานไม่เต็มประสิทธิภาพ

| ทางเลือก       | ลงทะเบียน | เช็กอิน | ประเมิน | เกียรติบัตร | ไม่ต้องโหลดแอป |
| -------------- | --------- | ------- | ------- | ----------- | -------------- |
| Google Form    | ✓         | ✗       | ✓       | ✗           | ✓              |
| Eventbrite     | ✓         | บางส่วน | ✗       | บางส่วน     | ✗              |
| Excel + กระดาษ | ✓         | ✓       | ✗       | ✗           | ✓              |
| **ระบบของเรา** | ✓         | ✓       | ✓       | ✓           | ✓              |

ช่องว่างที่ไม่มีทางเลือกไหนเติมครบ คือ **เช็กอิน + ประเมิน + เกียรติบัตร อยู่ในที่เดียว โดยที่ผู้เข้าร่วมไม่ต้องโหลดแอปเพิ่ม** — ซึ่งเป็นจุดที่ระบบนี้เข้ามาตอบโจทย์

## Research & Insight

### ข้อสังเกตจากงานจริง

จากงานนิทรรศการและกิจกรรมในคณะที่ผ่านมา การลงทะเบียนยังพึ่งใบเซ็นชื่อกระดาษหน้างาน แบบประเมินถูกแยกไปเป็นอีกหนึ่งลิงก์ และเกียรติบัตรต้องรอประมวลผลเป็นสัปดาห์กว่าจะถึงมือผู้เข้าร่วม ทำให้ข้อมูลกระจัดกระจาย ตรวจสอบย้อนหลังยาก และผู้จัดงานต้องมานั่งรวมข้อมูลด้วยมือ

### Insight → Design Decision

| Insight                                  | สิ่งที่ตัดสินใจทำ                                    |
| ---------------------------------------- | --------------------------------------------------- |
| ผู้เข้าร่วมไม่ยอมโหลดแอปเพื่องานวันเดียว | ใช้ LINE OA + LIFF แทนการทำแอปแยก                   |
| ผู้ใช้มี 3 บทบาทที่ต้องการคนละอย่าง      | แยก Organizer / Unit / Visitor ตั้งแต่ระดับฐานข้อมูล |
| ผู้จัดงานต้องปรับแผนหน้างานได้           | Dashboard สถิติเรียลไทม์บนเว็บ                      |
| เกียรติบัตรพิมพ์ผิด/ออกช้า               | ระบบออก PDF อัตโนมัติตามเกณฑ์ที่ตั้งไว้             |

### Tech Decision Log

- **Fastify แทน Express** — overhead ต่ำกว่าและมี JSON Schema Validation ในตัว เหมาะกับ Webhook ที่ถี่จัดช่วงคนเข้างานพร้อมกัน
- **MySQL แทน NoSQL** — เล่มออกแบบฐานข้อมูลเป็น 3 โดเมน (Exhibition / Unit / Survey) ที่เชื่อมโยงกันโดยมีตาราง `exhibition` เป็นศูนย์กลาง ข้อมูลจึงสัมพันธ์กันหลายชั้นและต้องรักษาความถูกต้องด้วย Transaction
- **TypeScript** — กำหนด type ร่วมกันระหว่าง client และ backend ลดบั๊กจากรูปร่างข้อมูลที่เปลี่ยนไปมา
- **Docker** — ล็อกสภาพแวดล้อมให้เหมือนกันทั้งเครื่อง dev และตอน deploy ลดปัญหา "เครื่องผมรันได้"

ผล benchmark ที่ทำให้เลือก Fastify: throughput สูงกว่า Express ราว 1.8 เท่า และอยู่ในกลุ่มหัวตารางเมื่อเทียบกับเฟรมเวิร์ก Node.js ตัวอื่น

## Goals & Scope

### เป้าหมายของโครงงาน

1. รวมการจัดการนิทรรศการทั้งหมด — ข้อมูลงาน บูธกิจกรรม ข่าวสาร แบบประเมิน และเกียรติบัตร — ไว้ในระบบเดียว
2. ให้ผู้เข้าร่วมลงทะเบียนและตรวจสอบสถานะการเข้าร่วมได้เองผ่าน LINE OA โดยไม่ต้องติดตั้งแอปเพิ่ม
3. ให้ผู้ดูแลระบบและผู้จัดนิทรรศการจัดการข้อมูล (เพิ่ม/แก้ไข/ลบ) ได้จากหน้าเดียว
4. สร้างแบบประเมินความพึงพอใจ พร้อมประมวลผลและสรุปคะแนนอัตโนมัติ
5. ออกใบประกาศนียบัตรอิเล็กทรอนิกส์ให้ผู้ที่เข้าร่วมครบตามเกณฑ์โดยอัตโนมัติ

### ขอบเขตงาน

| ✅ In Scope (ทำจริงในเล่ม)                          | ❌ Out of Scope                       |
| --------------------------------------------------- | ------------------------------------- |
| ลงทะเบียน/เช็กอินผ่าน QR Code                       | ระบบชำระเงินและออกใบเสร็จ             |
| ใช้งานผ่าน LINE Application (LIFF + Messaging API)  | แอป Native iOS/Android                |
| CRUD ข้อมูลนิทรรศการและบูธกิจกรรม                   | ระบบจองรอบเวลา/ที่นั่ง                |
| เผยแพร่ข่าวสารและแจ้งเตือนผ่าน LINE                 | รองรับหลายภาษา                        |
| สร้างแบบประเมิน + ประมวลผลสรุปคะแนน                 | วิเคราะห์ข้อมูลเชิงลึกด้วย AI         |
| ตรวจสอบสถานะการเข้าร่วมกิจกรรม                      | ระบบ live streaming / งานออนไลน์      |
| ออก E-Certificate เป็น PDF อัตโนมัติ                | การเชื่อมต่อระบบทะเบียนของมหาวิทยาลัย |

เหตุผลที่ตัดออก:

- **ไม่ทำแอป Native iOS/Android** — เลือก LINE โดยตั้งใจเพื่อลด friction ให้ผู้ใช้ไม่ต้องติดตั้งแอปเพิ่ม
- **ไม่เชื่อมต่อระบบทะเบียนของมหาวิทยาลัย** — ลดการพึ่งพาระบบภายนอกที่ควบคุมไม่ได้ เพื่อให้ส่งมอบได้ตามกำหนด
- **ไม่รองรับหลายภาษา** — ผู้ใช้งานหลักคืองานนิทรรศการภายในคณะ จึงยังไม่จำเป็นต้องรองรับหลายภาษา

### เกณฑ์วัดความสำเร็จ

ตั้งเกณฑ์ไว้ 5 ด้าน และวัดผลจริงทุกข้อ (ผลการทดสอบอยู่ในหัวข้อ Results & Impact)

- **ความถูกต้องของ API** — ทดสอบทุก endpoint ด้วย Postman ตรวจ HTTP Status Code
- **ความสมบูรณ์ของข้อมูล** — ตรวจโครงสร้าง JSON Response ว่าตรงตามที่ออกแบบ
- **ความครอบคลุมของ API** — ทดสอบทั้ง 6 ระบบย่อย โดยระบบนิทรรศการ / บูธกิจกรรม / ข่าวสาร ต้องรองรับ CRUD ครบทั้ง 4 รูปแบบ
- **ส่วนติดต่อผู้ใช้** — UI Testing ทุกหน้าจอ ทำงานตามที่ออกแบบ
- **การใช้งานจริง** — นำระบบไปใช้กับงานจริง บันทึกและประมวลผลข้อมูลได้ถูกต้อง

### แผนงานและข้อจำกัด

แผนงาน 10 เดือนจากเล่ม (หน้า 2–4) ยุบเหลือ 4 เฟสหลัก — ภาค 1 (ก.ค.–พ.ย. 2568) ออกแบบ + พัฒนาระบบจัดการหลัก / ภาค 2 (ธ.ค. 2568–เม.ย. 2569) เชื่อม LINE, QR, แบบประเมิน, เกียรติบัตร

| เฟส                 | ช่วงเวลา             | สิ่งที่ทำ                                           |
| ------------------- | -------------------- | --------------------------------------------------- |
| Research & Analysis | ก.ค.–ส.ค. 2568       | ศึกษาข้อมูล วิเคราะห์ความต้องการ                    |
| Design              | ก.ย.–ต.ค. 2568       | ออกแบบ UI (Figma), ER Diagram, System Architecture  |
| Development         | พ.ย. 2568–ก.พ. 2569  | พัฒนา Frontend/Backend, เชื่อม LINE OA              |
| Testing & Deploy    | มี.ค.–เม.ย. 2569     | UI Testing, Postman API Testing, นำเสนอผลงาน        |

- **ข้อจำกัดแพลตฟอร์ม:** LINE OA บัญชีฟรีมีโควต้า push message จำกัด
- **ข้อสมมติ:** ผู้เข้าร่วมมี LINE บนสมาร์ตโฟนและเชื่อมต่ออินเทอร์เน็ตได้หน้างาน
- **สถานะ:** เสร็จสมบูรณ์ ผ่านการสอบปริญญานิพนธ์ เม.ย. 2569

## Role & Contribution

ทีม 2 คน (ณัฐวัฒน์ + ยงศักดิ์) — เล่มไม่ได้แยกบทบาทไว้ชัดเจน จึงสรุปส่วนที่ผมรับผิดชอบไว้ดังนี้

- ออกแบบและพัฒนา REST API ด้วย Fastify ครอบคลุม 6 โมดูล (นิทรรศการ / บูธกิจกรรม / แบบประเมิน / เกียรติบัตร / ข่าวสาร / ตรวจสอบการเข้าร่วม)
- เชื่อมต่อ LINE Messaging API และ LIFF สำหรับลงทะเบียน เช็กอิน และแจ้งเตือน
- ออกแบบ ER Diagram และโครงสร้างฐานข้อมูล MySQL 14 ตาราง
- ตั้งค่า Docker และ Cloudflare Tunnel สำหรับ dev/test

ขอให้เครดิต **ณัฐวัฒน์** เพื่อนร่วมทีมที่ช่วยรับผิดชอบงานส่วนอื่นของโครงงานร่วมกันจนส่งมอบได้สำเร็จ

ทำงานภายใต้การดูแลของ **อ.อรรถศาสตร์ นาคเทวัญ**

## The Solution

ระบบออกแบบให้ผู้ใช้ 3 กลุ่มเห็นข้อมูลคนละมุม — **ผู้จัดงาน** จัดการข้อมูลและดูสถิติทั้งงาน, **เจ้าหน้าที่ประจำบูธ** เช็กอินผู้เข้าร่วมเฉพาะบูธตัวเอง, และ **ผู้เข้าร่วมงาน** ลงทะเบียน ทำแบบประเมิน และรับเกียรติบัตรผ่าน LINE

### โครงสร้างฐานข้อมูล

ตาราง 14 ตารางถูกแบ่งเป็น 3 โดเมนหลักเพื่อให้เห็นขอบเขตชัดเจน

- **Exhibition** — `exhibition`, `registrations`, `exhibition_announcements`, `certificate_templates`, `normal_users`
- **Unit** — `unit`, `unit_staffs`, `units_checkins`
- **Survey** — `question_sets`, `questions_template`, `set_question_mapping`, `survey_submissions`, `survey_answers`, `survey_tracking`

จุดที่ควรอธิบายเพิ่ม:

- **ทำไมแยก `question_sets` กับ `questions_template`** — แยก "ชุดคำถาม" ออกจาก "ตัวคำถาม" ทำให้เอาคำถามกลับมาใช้ซ้ำในหลายชุดได้ ไม่ต้องสร้างใหม่ทุกครั้ง
- **`survey_tracking` ทำหน้าที่อะไร** — ติดตามว่าใครทำแบบประเมินของชุดไหนไปแล้ว กันการตอบซ้ำและใช้เป็นเงื่อนไขออกเกียรติบัตร
- **ผูก LINE User ID กับ `normal_users` ยังไง** — เก็บ LINE User ID ที่ได้จาก LIFF/Webhook เป็นคีย์อ้างอิงใน `normal_users` เพื่อให้ระบุตัวตนผู้ใช้ข้ามช่องทางได้โดยไม่ต้องมี username/password

### ตัวอย่างโค้ด: Webhook Handler

```ts
// รับ event จาก LINE Messaging API แล้ว dispatch ตามชนิด event
app.post("/webhook", async (request, reply) => {
  const events = request.body.events;

  for (const event of events) {
    if (event.type === "message") {
      await handleMessage(event);
    } else if (event.type === "follow") {
      await handleFollow(event);
    }
  }

  return reply.code(200).send("OK");
});
```

## Challenges & Solutions

### 1. ทดสอบ Webhook และ LIFF บน localhost

**Situation** — LINE Messaging API และ LIFF ต้องเรียกผ่าน HTTPS endpoint ที่เข้าถึงจากอินเทอร์เน็ตได้ แต่ backend รันอยู่บน localhost ของเครื่อง dev ซึ่งไม่มี public URL

**Task** — ต้องทดสอบ flow จริงทั้งหมด (ลงทะเบียน → เช็กอิน → แบบประเมิน → E-Certificate) โดยไม่ต้อง deploy ขึ้น production ทุกครั้งที่แก้โค้ด

**Action** — ใช้ Cloudflare Tunnel เปิด public HTTPS endpoint ที่ชี้กลับมาที่เครื่อง dev โดยไม่ต้องตั้งค่า firewall หรือซื้อโดเมน และรัน tunnel ควบคู่กับ dev server ทุกครั้งที่ทดสอบ

**Result** — ทดสอบ flow จริงได้ครบทั้งหมดบนเครื่อง dev ลดรอบเวลาแก้บั๊กจากที่ต้อง deploy ก่อนตรวจสอบ เหลือแก้แล้วเห็นผลทันที และทีมทั้งสองคนแชร์ tunnel ให้กันทดสอบได้

```txt
LINE Platform ──HTTPS──▶ Cloudflare Edge ──tunnel──▶ localhost:3000 (Fastify)
```

### 2. ความซับซ้อนของโมดูลและบทบาทผู้ใช้

**Situation** — ระบบมี 6 โมดูล และผู้ใช้ 3 บทบาท (Organizer / Unit / Visitor) ที่มองข้อมูลคนละมุม

**Task** — ต้องกำหนดโครงสร้างข้อมูลและขอบเขตงานให้ชัดก่อนลงโค้ด เพื่อไม่ให้แก้ schema ระหว่างพัฒนา

**Action** — ออกแบบ ER Diagram และแบ่งโดเมนตารางให้ชัดก่อนเขียนโค้ด (Exhibition / Unit / Survey) พร้อมแบ่งหน้าที่ในทีมตั้งแต่ต้น

**Result** — ลดงานแก้ schema ย้อนหลัง และทั้งสองคนทำงานคู่ขนานได้โดยไม่ชนกัน

### 3. เครื่องมือใหม่ที่ทีมยังไม่คุ้น

**Situation** — เครื่องมือหลักที่เลือกใช้เป็นของใหม่สำหรับทีม ต่างจากที่เรียนมา

**Task** — ลดความเสี่ยงที่จะ integrate ไม่ผ่านเมื่อถึงเวลาประกอบระบบ

**Action** — ทำ prototype เล็กแยกก่อนต่อเข้าระบบจริง ทดลอง Webhook handler, LIFF login และ Docker compose ทีละส่วน

**Result** — เข้าใจข้อจำกัดของแต่ละเครื่องมือก่อน integrate จริง ลดปัญหาที่ต้องรื้อโค้ดทีหลัง

## Results & Impact

### ผลการทดสอบ

ผลทดสอบ 32 กรณีของส่วนติดต่อผู้ใช้ผ่านทั้งหมด และทดสอบส่วนประมวลผลหลังบ้าน (Backend API) ด้วย Postman ครบทั้ง 6 ระบบย่อย (บทที่ 4 หน้า 38–104)

| ระบบย่อย                       | กรณีทดสอบ                                     | ผลลัพธ์ |
| ------------------------------ | --------------------------------------------- | ------- |
| ระบบการจัดการนิทรรศการ         | CRUD ครบ 4 รูปแบบ (GET / POST / PUT / DELETE) | ผ่าน    |
| ระบบการจัดการบูธกิจกรรม        | CRUD + สร้าง QR และเช็กอินรายบูธ              | ผ่าน    |
| ระบบการจัดการแบบประเมิน        | จัดการชุดคำถาม + ตอบแบบประเมินผ่าน LIFF       | ผ่าน    |
| ระบบการจัดการใบประกาศนียบัตร   | จัดการ template + ดู/ดาวน์โหลดผ่าน LIFF       | ผ่าน    |
| ระบบการแจ้งข้อมูลข่าวสาร       | CRUD ครบ 4 รูปแบบ                             | ผ่าน    |
| ระบบตรวจสอบการเข้าร่วมกิจกรรม  | สร้าง QR + เจ้าหน้าที่สแกนบันทึกการเช็กอิน     | ผ่าน    |

**Impact เชิงกระบวนการ:** จากลงชื่อกระดาษ + แบบประเมินคนละลิงก์ + เกียรติบัตรพิมพ์เอง → เหลือช่องทางเดียวใน LINE

### บทเรียนและก้าวต่อไป

**สิ่งที่อยากทำต่อ** — จากข้อเสนอแนะในเล่ม (หน้า 106)

- รองรับ Broadcast Message เต็มรูปแบบเพื่อแจ้งข่าวแบบเรียลไทม์
- ปรับปรุง response time ของระบบ
- พัฒนา UI ให้ใช้ง่ายและดึงดูดขึ้น

**บทเรียนที่ได้**

- การออกแบบฐานข้อมูลก่อนเขียนโค้ดช่วยลดงานแก้ทีหลัง
- ข้อจำกัดของแพลตฟอร์มภายนอก (LINE) ต้องรู้ตั้งแต่ต้น
- การแบ่งงานในทีม 2 คนต้องกำหนดขอบเขตชัด

**ถ้าย้อนกลับไปจะทำต่าง** — ควรวางแผนเก็บผลประเมินจากผู้ใช้จริงตั้งแต่ต้น ไม่ใช่เก็บเฉพาะผลทดสอบเชิงเทคนิค เพราะ Feedback จากผู้ใช้จริงจะบอกได้ว่าฟีเจอร์ไหนมีค่าและควรปรับก่อนส่งมอบ
