## ปัญหาและผลกระทบ

การจัดนิทรรศการและกิจกรรมในปัจจุบันยังพึ่งพากระบวนการแบบกระจัดกระจาย ผู้เข้าร่วมลงชื่อบนกระดาษหน้างาน ทำแบบประเมินผ่านลิงก์อีกช่องทาง แล้วรอรับเกียรติบัตรทางอีเมลอีกหลายวันให้หลัง ขณะที่ผู้จัดงานต้องนำข้อมูลจากทุกช่องทางมารวมด้วยมือ เพื่อตรวจสอบว่าใครเข้าร่วมครบตามเกณฑ์บ้าง

| ฝั่งผู้จัดงาน                                          | ฝั่งผู้เข้าร่วม                                   |
| ------------------------------------------------------ | ------------------------------------------------- |
| ต้องรวมข้อมูลจากหลายระบบด้วยมือ เสี่ยงตกหล่นและซ้ำซ้อน | ไม่รู้ว่าตัวเองเข้าร่วมครบตามเกณฑ์แล้วหรือยัง     |
| ไม่เห็นยอดผู้เข้าร่วมระหว่างงาน ปรับแผนหน้างานไม่ได้   | ต้องเดินไปถามทีมงาน หรือรอให้ประกาศผล             |
| ออกเกียรติบัตรทีละใบ ใช้เวลานานและพิมพ์ชื่อผิดบ่อย     | ได้รับเกียรติบัตรช้า บางครั้งชื่อสะกดผิดต้องขอแก้ |
| ใช้กระดาษจำนวนมากทั้งใบเซ็นชื่อและเกียรติบัตร          | ทำเอกสารหายแล้วขอใหม่ไม่ได้                       |

### ทางเลือกที่มีอยู่ไม่ตอบโจทย์

ระบบจัดการงานอีเวนต์ที่มีในตลาดมักอยู่ในรูปแบบแอปพลิเคชันที่ต้องติดตั้งและสมัครสมาชิกใหม่ ซึ่งเป็นอุปสรรคสำคัญกับงานที่มีผู้เข้าร่วมหลากหลายกลุ่มและใช้งานเพียงครั้งเดียว ผู้เข้าร่วมจำนวนมากไม่ยอมโหลดแอปเพื่อร่วมงานเพียงวันเดียว ทำให้ระบบถูกใช้งานไม่เต็มประสิทธิภาพ

| ทางเลือก       | ลงทะเบียน | เช็กอิน | ประเมิน | เกียรติบัตร | ไม่ต้องโหลดแอป |
| -------------- | --------- | ------- | ------- | ----------- | -------------- |
| Google Form    | ✓         | ✗       | ✓       | ✗           | ✓              |
| Excel + กระดาษ | ✓         | ✓       | ✗       | ✗           | ✓              |
| **ระบบของเรา** | ✓         | ✓       | ✓       | ✓           | ✓              |

ช่องว่างที่ไม่มีทางเลือกไหนเติมครบ คือ **เช็กอิน + ประเมิน + เกียรติบัตร อยู่ในที่เดียว โดยที่ผู้เข้าร่วมไม่ต้องโหลดแอปเพิ่ม** — ซึ่งเป็นจุดที่ระบบนี้เข้ามาตอบโจทย์

## ข้อสังเกตจากงานจริง

จากงานนิทรรศการและกิจกรรมในคณะที่ผ่านมา การลงทะเบียนยังพึ่งใบเซ็นชื่อกระดาษหน้างาน แบบประเมินถูกแยกไปเป็นอีกหนึ่งลิงก์ และเกียรติบัตรต้องรอประมวลผลเป็นสัปดาห์กว่าจะถึงมือผู้เข้าร่วม ทำให้ข้อมูลกระจัดกระจาย ตรวจสอบย้อนหลังยาก และผู้จัดงานต้องมานั่งรวมข้อมูลด้วยมือ

| ข้อสังเกตที่พบ                           | สิ่งที่ตัดสินใจทำ                                    |
| ---------------------------------------- | ---------------------------------------------------- |
| ผู้เข้าร่วมไม่ยอมโหลดแอปเพื่องานวันเดียว | ใช้ LINE OA + LIFF แทนการทำแอปแยก                    |
| ผู้ใช้มี 3 บทบาทที่ต้องการคนละอย่าง      | แยก Organizer / Unit / Visitor ตั้งแต่ระดับฐานข้อมูล |
| ผู้จัดงานต้องปรับแผนหน้างานได้           | Dashboard สถิติเรียลไทม์บนเว็บ                       |
| เกียรติบัตรพิมพ์ผิด/ออกช้า               | ระบบออก PDF อัตโนมัติตามเกณฑ์ที่ตั้งไว้              |

### เลือกเครื่องมือที่ใช้

- **Fastify แทน Express** — overhead ต่ำกว่าและมี JSON Schema Validation ในตัว เหมาะกับ Webhook ที่ถี่จัดช่วงคนเข้างานพร้อมกัน
- **MySQL แทน NoSQL** — เล่มออกแบบฐานข้อมูลเป็น 3 โดเมน (Exhibition / Unit / Survey) ที่เชื่อมโยงกันโดยมีตาราง `exhibition` เป็นศูนย์กลาง ข้อมูลจึงสัมพันธ์กันหลายชั้นและต้องรักษาความถูกต้องด้วย Transaction
- **TypeScript** — กำหนด type ร่วมกันระหว่าง client และ backend ลดบั๊กจากรูปร่างข้อมูลที่เปลี่ยนไปมา
- **Docker** — ล็อกสภาพแวดล้อมให้เหมือนกันทั้งเครื่อง dev และตอน deploy ลดปัญหา "เครื่องผมรันได้"

ผล benchmark ที่ทำให้เลือก Fastify: throughput สูงกว่า Express ราว 1.8 เท่า และอยู่ในกลุ่มหัวตารางเมื่อเทียบกับเฟรมเวิร์ก Node.js ตัวอื่น

## เป้าหมายและขอบเขต

### เป้าหมายของโครงงาน

1. รวมการจัดการนิทรรศการทั้งหมด — ข้อมูลงาน บูธกิจกรรม ข่าวสาร แบบประเมิน และเกียรติบัตร — ไว้ในระบบเดียว
2. ให้ผู้เข้าร่วมลงทะเบียนและตรวจสอบสถานะการเข้าร่วมได้เองผ่าน LINE OA โดยไม่ต้องติดตั้งแอปเพิ่ม
3. ให้ผู้ดูแลระบบและผู้จัดนิทรรศการจัดการข้อมูล (เพิ่ม/แก้ไข/ลบ) ได้จากหน้าเดียว
4. สร้างแบบประเมินความพึงพอใจ พร้อมประมวลผลและสรุปคะแนนอัตโนมัติ
5. ออกใบประกาศนียบัตรอิเล็กทรอนิกส์ให้ผู้ที่เข้าร่วมครบตามเกณฑ์โดยอัตโนมัติ

### ขอบเขตงาน

- ลงทะเบียน/เช็กอินผ่าน QR Code
- ใช้งานผ่าน LINE Application (LIFF + Messaging API)
- CRUD ข้อมูลนิทรรศการและบูธกิจกรรม
- เผยแพร่ข่าวสารและแจ้งเตือนผ่าน LINE
- สร้างแบบประเมิน + ประมวลผลสรุปคะแนน
- ตรวจสอบสถานะการเข้าร่วมกิจกรรม
- ออก E-Certificate เป็น PDF อัตโนมัติ

### เกณฑ์วัดความสำเร็จ

ตั้งเกณฑ์ไว้ 5 ด้าน และวัดผลจริงทุกข้อ

- **ความถูกต้องของ API** — ทดสอบทุก endpoint ด้วย Postman ตรวจ HTTP Status Code
- **ความสมบูรณ์ของข้อมูล** — ตรวจโครงสร้าง JSON Response ว่าตรงตามที่ออกแบบ
- **ความครอบคลุมของ API** — ทดสอบทั้ง 6 ระบบย่อย โดยระบบนิทรรศการ / บูธกิจกรรม / ข่าวสาร ต้องรองรับ CRUD ครบทั้ง 4 รูปแบบ
- **ส่วนติดต่อผู้ใช้** — UI Testing ทุกหน้าจอ ทำงานตามที่ออกแบบ
- **การใช้งานจริง** — นำระบบไปใช้กับงานจริง บันทึกและประมวลผลข้อมูลได้ถูกต้อง

### แผนงานและข้อจำกัด

แผนงาน ภาคเรียนที่ 1 (ก.ค.–พ.ย. 2568) ออกแบบ + พัฒนาระบบจัดการหลัก / ภาคเรืยนที่ 2 (ธ.ค. 2568–เม.ย. 2569) เชื่อม LINE, QR, แบบประเมิน, เกียรติบัตร

| เฟส                 | ช่วงเวลา            | สิ่งที่ทำ                                          |
| ------------------- | ------------------- | -------------------------------------------------- |
| Research & Analysis | ก.ค.–ส.ค. 2568      | ศึกษาข้อมูล วิเคราะห์ความต้องการ                   |

| Development         | พ.ย. 2568–ก.พ. 2569 | พัฒนา Frontend/Backend, เชื่อม LINE OA             |

- **ข้อจำกัดแพลตฟอร์ม:** LINE OA บัญชีฟรีมีโควต้า push message จำกัด
- **ข้อสมมติ:** ผู้เข้าร่วมมี LINE บนสมาร์ตโฟนและเชื่อมต่ออินเทอร์เน็ตได้หน้างาน
- **สถานะ:** เสร็จสมบูรณ์ ผ่านการสอบปริญญานิพนธ์ เม.ย. 2569

## บทบาทและหน้าที่

ทีม 2 คน แบ่งขอบเขตงานกันชัดเจน — เล่มไม่ได้แยกบทบาทไว้ จึงสรุปไว้ดังนี้

**ยงศักดิ์ (ผม) — Backend & Infrastructure**

- ออกแบบและพัฒนา REST API ด้วย Fastify ครอบคลุม 6 โมดูล (นิทรรศการ / บูธกิจกรรม / แบบประเมิน / เกียรติบัตร / ข่าวสาร / ตรวจสอบการเข้าร่วม)
- เชื่อมต่อ LINE Messaging API และ LIFF สำหรับลงทะเบียน เช็กอิน และแจ้งเตือน
- ตั้งค่า Docker และ Cloudflare Tunnel สำหรับ dev/test

**ณัฐวัฒน์ (เพื่อนร่วมทีม) — UI Design & Frontend**

- ออกแบบ UI ทั้งระบบด้วย Figma
- พัฒนา Frontend ด้วย React + TypeScript ครอบคลุมหน้าจอผู้จัดงานทั้ง 6 โมดูล
- พัฒนาหน้า LIFF ให้ผู้เข้าร่วมใช้งานผ่าน LINE บนมือถือ (ลงทะเบียน / เช็กอิน / แบบประเมิน / รับเกียรติบัตร)
- เชื่อมต่อ REST API จาก Backend เข้ากับ UI จัดการ state และฟอร์มของแต่ละหน้า

**ร่วมกัน — Database Design**

- ออกแบบ ER Diagram และโครงสร้างฐานข้อมูล MySQL 14 ตาราง

ขอให้เครดิต **ณัฐวัฒน์** เพื่อนร่วมทีมที่ช่วยรับผิดชอบงานส่วนอื่นของโครงงานร่วมกันจนส่งมอบได้สำเร็จ

ทำงานภายใต้การดูแลของ **อ.อรรถศาสตร์ นาคเทวัญ**

### ตัวอย่างโค้ด: Webhook Handler

จุดที่รับ Webhook ไม่ใช่แค่ dispatch เหตุการณ์ แต่โฟกัสที่ **ยืนยันลายเซ็น** ก่อน (ป้องกันใครปลอม requests หลอกระบบ) แล้วค่อยกระจาย event ไปยัง handler

```ts
// จุดรับ Webhook จาก LINE
app.post(
  "/webhook",
  { config: { rawBody: true } }, // ต้องอ่าน raw body เพื่อเอาไปคำนวณ HMAC
  async (req: RawBodyRequest, reply: FastifyReply) => {
    const signature = req.headers["x-line-signature"];
    if (typeof signature !== "string") {
      return reply.code(400).send({ message: "missing LINE signature header" });
    }

    // ยืนยันว่า payload มาจาก LINE จริง ๆ (HMAC-SHA256 ด้วย Channel Secret)
    if (!verifyLineSignature(signature, req.rawBody, getLineConfig())) {
      return reply.code(401).send({ message: "invalid LINE signature" });
    }

    const events = (req.body as LineWebhookPayload)?.events ?? [];
    if (!events.length) {
      return reply.send({ ok: true });
    }

    // dispatch ทั้งหมดพร้อมกัน — event หนึ่งผิดพลาดไม่ฉุด event อื่น
    await Promise.all(
      events.map((event) =>
        dispatchLineEvent(event, getLineConfig(), app.log).catch((err) => {
          app.log.error({ err, event }, "failed to process LINE event");
        }),
      ),
    );

    reply.send({ ok: true });
  },
);
```

ตัวกระจายเหตุการณ์จะตัดสินใจตามชนิด event แล้วเรียก handler ที่รับผิดชอบ

```ts
export async function dispatchLineEvent(event, config, log) {
  const userId = event.source?.userId;

  if (event.type === "unfollow" && userId) {
    await markLineUserUnfollowed(userId); // ลบ soft-delete เลิกติดตาม
    return;
  }

  // ดึงโปรไฟล์ LINE มาซิงก์เข้า normal_users ทุกครั้งที่ใช้งาน
  const profile = await fetchLineProfile(userId, config);
  await upsertLineUserProfile({
    line_user_id: profile.userId,
    display_name: profile.displayName,
    picture_url: profile.pictureUrl ?? null,
  });

  if (event.type === "follow" && event.replyToken) {
    return handleFollowEvent(event.replyToken, config, log);
  }
  if (event.type === "postback" && event.postback?.data) {
    return handlePostbackEvent(
      event.replyToken,
      userId,
      event.postback.data,
      config,
      log,
    );
  }
  if (event.type === "message" && event.message?.type === "text") {
    return handleMessageCommand(
      event.replyToken,
      userId,
      event.message.text,
      config,
      log,
    );
  }
}
```

## ความท้าทายและการแก้ไขปัญหา

### 1. ทดสอบ Webhook และ LIFF บน localhost

**สถานการณ์** — LINE Messaging API และ LIFF ต้องเรียกผ่าน HTTPS endpoint ที่เข้าถึงจากอินเทอร์เน็ตได้ แต่ backend รันอยู่บน localhost ของเครื่อง dev ซึ่งไม่มี public URL

**สิ่งที่ต้องทำ** — ต้องทดสอบ flow จริงทั้งหมด (ลงทะเบียน → เช็กอิน → แบบประเมิน → E-Certificate) โดยไม่ต้อง deploy ขึ้น production ทุกครั้งที่แก้โค้ด

**ทางแก้ไข** — ใช้ Cloudflare Tunnel เปิด public HTTPS endpoint ที่ชี้กลับมาที่เครื่อง dev โดยไม่ต้องตั้งค่า firewall หรือซื้อโดเมน และรัน tunnel ควบคู่กับ dev server ทุกครั้งที่ทดสอบ

**ผลลัพธ์** — ทดสอบ flow จริงได้ครบทั้งหมดบนเครื่อง dev ลดรอบเวลาแก้บั๊กจากที่ต้อง deploy ก่อนตรวจสอบ เหลือแก้แล้วเห็นผลทันที และทีมทั้งสองคนแชร์ tunnel ให้กันทดสอบได้

### 2. ความซับซ้อนของโมดูลและบทบาทผู้ใช้

**สถานการณ์** — ระบบมี 6 โมดูล และผู้ใช้ 3 บทบาท (Organizer / Unit / Visitor) ที่มองข้อมูลคนละมุม

**สิ่งที่ต้องทำ** — ต้องกำหนดโครงสร้างข้อมูลและขอบเขตงานให้ชัดก่อนลงโค้ด เพื่อไม่ให้แก้ schema ระหว่างพัฒนา

**ทางแก้ไข** — ออกแบบ ER Diagram และแบ่งโดเมนตารางให้ชัดก่อนเขียนโค้ด (Exhibition / Unit / Survey) พร้อมแบ่งหน้าที่ในทีมตั้งแต่ต้น

**ผลลัพธ์** — ลดงานแก้ schema ย้อนหลัง และทั้งสองคนทำงานคู่ขนานได้โดยไม่ชนกัน

### 3. เครื่องมือใหม่ที่ทีมยังไม่คุ้น

**สถานการณ์** — เครื่องมือหลักที่เลือกใช้เป็นของใหม่สำหรับทีม ต่างจากที่เรียนมา

**สิ่งที่ต้องทำ** — ลดความเสี่ยงที่จะ integrate ไม่ผ่านเมื่อถึงเวลาประกอบระบบ

**ทางแก้ไข** — ทำ prototype เล็กแยกก่อนต่อเข้าระบบจริง ทดลอง Webhook handler, LIFF login และ Docker compose ทีละส่วน

**ผลลัพธ์** — เข้าใจข้อจำกัดของแต่ละเครื่องมือก่อน integrate จริง ลดปัญหาที่ต้องรื้อโค้ดทีหลัง

### บทเรียนและก้าวต่อไป

**สิ่งที่อยากทำต่อ**

- รองรับ Broadcast Message เต็มรูปแบบเพื่อแจ้งข่าวแบบเรียลไทม์
- ปรับปรุง response time ของระบบ
- พัฒนา UI ให้ใช้ง่ายและดึงดูดขึ้น

**บทเรียนที่ได้**

- การออกแบบฐานข้อมูลก่อนเขียนโค้ดช่วยลดงานแก้ทีหลัง
- ข้อจำกัดของแพลตฟอร์มภายนอก (LINE) ต้องรู้ตั้งแต่ต้น
- การแบ่งงานในทีม 2 คนต้องกำหนดขอบเขตชัด
