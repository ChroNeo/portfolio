## ปัญหาที่พบ

การจัดนิทรรศการและกิจกรรมในปัจจุบันยังพึ่งพากระบวนการแบบกระจัดกระจาย ผู้เข้าร่วมลงชื่อบนกระดาษหน้างาน ทำแบบประเมินผ่านลิงก์อีกช่องทาง แล้วรอรับเกียรติบัตรทางอีเมลอีกหลายวันให้หลัง ขณะที่ผู้จัดงานต้องนำข้อมูลจากทุกช่องทางมารวมด้วยมือ เพื่อตรวจสอบว่าใครเข้าร่วมครบตามเกณฑ์บ้าง

### ผลกระทบที่เกิดขึ้นจริง

| ฝั่งผู้จัดงาน                                          | ฝั่งผู้เข้าร่วม                                   |
| ------------------------------------------------------ | ------------------------------------------------- |
| ต้องรวมข้อมูลจากหลายระบบด้วยมือ เสี่ยงตกหล่นและซ้ำซ้อน | ไม่รู้ว่าตัวเองเข้าร่วมครบตามเกณฑ์แล้วหรือยัง     |
| ไม่เห็นยอดผู้เข้าร่วมระหว่างงาน ปรับแผนหน้างานไม่ได้   | ต้องเดินไปถามทีมงาน หรือรอให้ประกาศผล             |
| ออกเกียรติบัตรทีละใบ ใช้เวลานานและพิมพ์ชื่อผิดบ่อย     | ได้รับเกียรติบัตรช้า บางครั้งชื่อสะกดผิดต้องขอแก้ |
| ใช้กระดาษจำนวนมากทั้งใบเซ็นชื่อและเกียรติบัตร          | ทำเอกสารหายแล้วขอใหม่ไม่ได้                       |

### ข้อจำกัดของทางออกที่มีอยู่

ระบบจัดการงานอีเวนต์ที่มีในตลาดมักอยู่ในรูปแบบแอปพลิเคชันที่ต้องติดตั้งและสมัครสมาชิกใหม่ ซึ่งเป็นอุปสรรคสำคัญกับงานที่มีผู้เข้าร่วมหลากหลายกลุ่มและใช้งานเพียงครั้งเดียว ผู้เข้าร่วมจำนวนมากไม่ยอมโหลดแอปเพื่อร่วมงานเพียงวันเดียว ทำให้ระบบถูกใช้งานไม่เต็มประสิทธิภาพ

## ข้อสังเกตจากงานจริง

จากงานนิทรรศการและกิจกรรมในคณะที่ผ่านมา การลงทะเบียนยังพึ่งใบเซ็นชื่อกระดาษหน้างาน
แบบประเมินถูกแยกไปเป็นอีกหนึ่งลิงก์ และเกียรติบัตรต้องรอประมวลผลเป็นสัปดาห์กว่าจะถึงมือผู้เข้าร่วม
ทำให้ข้อมูลกระจัดกระจาย ตรวจสอบย้อนหลังยาก และผู้จัดงานต้องมานั่งรวมข้อมูลด้วยมือ

ช่องว่างที่ไม่มีทางเลือกไหนเติมครบ คือ **เช็กอิน + ประเมิน + เกียรติบัตร อยู่ในที่เดียว
โดยที่ผู้เข้าร่วมไม่ต้องโหลดแอปเพิ่ม** — ซึ่งเป็นจุดที่ระบบนี้เข้ามาตอบโจทย์

## Tech Decision Log

- **Fastify แทน Express** — overhead ต่ำกว่าและมี JSON Schema Validation ในตัว เหมาะกับ Webhook ที่ถี่จัดช่วงคนเข้างานพร้อมกัน
- **MySQL แทน NoSQL** — ข้อมูลมีความสัมพันธ์กันหลายชั้น (Exhibition / Unit / Survey) และต้องใช้ Transaction ในการรับประกันความถูกต้อง
- **TypeScript** — กำหนด type ร่วมกันระหว่าง client และ backend ลดบั๊กจากรูปร่างข้อมูลที่เปลี่ยนไปมา
- **Docker** — ล็อกสภาพแวดล้อมให้เหมือนกันทั้งเครื่อง dev และตอน deploy ลดปัญหา "เครื่องผมรันได้"

ขอบเขตที่ระบบ **ยังไม่ทำ** ในเวอร์ชันนี้: การส่ง Broadcast Message ถึงผู้เข้าร่วมทั้งหมด
พร้อมกัน (ติดข้อจำกัดของแพ็กเกจ LINE OA แบบฟรี) และระบบชำระเงินสำหรับงานที่มีค่าลงทะเบียน

ระบบแบ่งออกเป็น 3 ชั้นหลัก:

1. **ฝั่งผู้ใช้ (Client)** — LINE Official Account + LIFF (LINE Front-end Framework)
   สำหรับหน้าจอลงทะเบียน แบบประเมิน และแสดงใบประกาศนียบัตร ทำงานอยู่ภายในแอป LINE
   โดยตรง โดยใช้ `React + TypeScript`
2. **ฝั่ง Backend** — Fastify (Node.js + TypeScript) รับ Webhook Event จาก LINE,
   ประมวลผล Business Logic และให้บริการ REST API แก่หน้าแดชบอร์ดของผู้จัดงาน
3. **ฐานข้อมูล** — MySQL แบ่งเป็น 3 โดเมนหลัก (Exhibition / Unit / Survey) เชื่อมโยง
   กันผ่านตาราง `exhibitions` เป็นศูนย์กลาง

## ปัญหาการรองรับ Traffic

**ปัญหาการใช้งานจริง:** การจัดงานนิทรรศการมักเจอปัญหารอคิวนาน เอกสารกระดาษสูญหาย และการออกใบประกาศนียบัตรล่าช้า

**ความท้าทายฝั่ง Backend:** เกิด **Burst Traffic** หรือคำขอเข้าสู่ระบบพร้อมกันจำนวนมากในช่วงเวลาสั้นๆ (เช่น ผู้เข้าร่วมสแกน QR Code เข้าบูธพร้อมกันหลายร้อยคน)

**เป้าหมายสถาปัตยกรรม:** ออกแบบระบบหลังบ้านที่ตอบสนองไว (Low Latency) มีเสถียรภาพ และจัดการข้อมูลที่มีความสัมพันธ์ซับซ้อนได้อย่างถูกต้อง

## ทำไมต้องเป็น Fastify และ LINE Messaging API?

**Fastify vs Express:**

- Fastify มี overhead ต่ำกว่า และใช้ JSON Schema Validation ในตัว
- รองรับ Throughput ได้สูงกว่า เหมาะกับการรับส่ง Webhook ที่ถี่มากๆ ช่วงคนเข้างานพร้อมกัน
  **LINE Messaging API + LIFF vs Native App:**
- ลด Friction ฝั่งผู้ใช้ ไม่ต้องดาวน์โหลดแอปเพิ่ม
- โยนภาระงาน Push notification และ UI หน้าบ้านบางส่วนให้โครงสร้างพื้นฐานของ LINE แล้วใช้ Backend เราจัดการเฉพาะ Webhook Data

## การแก้ปัญหาในการพัฒนาจริง

- **Challenge 1: Webhook Debugging บน Local Environment**

  - _ข้อจำกัด:_ LINE บังคับใช้ HTTPS Endpoint เท่านั้นในการส่ง Webhook และรัน LIFF
  - _ทางแก้:_ ใช้ **Cloudflare Tunnel** จำลอง HTTPS Endpoint จากเครื่อง Local เข้าสู่ระบบ เพื่อทดสอบ Webhook Payload และการรับส่งข้อมูลจริงก่อน Deploy

- **Challenge 2: Data Integrity & Certificate Conditions**

  - _ข้อจำกัด:_ ต้องตรวจสอบเงื่อนไขการเช็คอินครบทุกบูธก่อนอนุญาตให้ทำแบบประเมินและรับใบประกาศฯ
  - _ทางแก้:_ ออกแบบ Index บน MySQL และปรับ Query ให้ตรวจเช็คเงื่อนไขความถูกต้อง (Transactional Check) ป้องกันการแจกใบประกาศฯ ซ้ำซ้อน
